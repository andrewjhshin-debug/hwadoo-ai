# 인연 사진 등록 보강

## 확인한 코드 문제와 수정

- 서버 Admin 초기화에 `storageBucket`이 없어 기본 bucket() 호출이 예외를 냈다. 실제 설치 SDK로 재현했고 브라우저·서버가 같은 공개 저장소 설정을 사용하게 했다.
- 업로드 오류를 화면에서 빈 문자열로 지우던 코드를 제거했다. 변환·전송·등록 단계를 표시하며 원인별 재시도를 안내한다.
- 등록·삭제·관리자 사진 심사에 트랜잭션을 적용해 동시 변경 시 사진 배열과 승인 상태가 유실되지 않게 했다.
- 같은 경로를 재등록하는 것은 성공으로 처리한다. 등록 확인은 15초 제한·최대 3회, 파일 전송은 120초 제한과 진행률을 둔다.
- 파일명은 UUID. 로그인 계정 변경을 확인하고, 잘못된 파일·0바이트·과대 파일은 거절한다. 원본 디코딩 실패 시 EXIF가 남는 원본을 그대로 올리지 않는다.
- 서버에서도 파일 메타데이터와 본인 단일 파일 경로를 검증한다. Storage 장애는 파일 없음과 구분한다.
- 여러 장 중 일부만 성공해도 목록을 갱신한다. 저장 실패인데 ‘저장됨’이 표시되던 처리도 바로잡았다.
- 심사 목록은 한 번에 40명, 비공개·캐시 금지·문서 ID 커서로 조회한다. 비어 있는 구간도 다음 커서를 제공해 뒤쪽 가입자가 누락되지 않게 한다.
- 즉석 인증 도전 발급 속도 제한과 제출을 트랜잭션으로 처리한다. 동일 인증 사진의 응답 유실 재시도는 성공으로 돌려준다.

## 자동 검증

`node scripts/yeon-photo-test.mjs`

실제 SDK의 기본 저장소 오류 재현, 파일·경로·인증 검증, 한 계정 30건 동시 등록의 5장 상한, 200명·1,000장 모의 등록, 중복·삭제 후 재등록, 인증 도전 동시 발급·중복 제출.

`node scripts/yeon-upload-test.mjs`

동일 경로 재시도, 토큰 갱신, 오프라인 재시도 상한, 계정 전환, 업로드 진행률·시간 초과 취소.

테스트의 DB·파일 저장은 모의 구현이며 실제 운영 동접·지연·요금 보장이 아니다. 사용자 얼굴 사진이나 실제 프로필을 테스트용으로 수정하지 않는다.

## 운영에서 추가 확인할 것

1. Android Chrome·iPhone에서 운영 계정이 아닌 테스트 계정으로 JPG/PNG/WEBP/HEIC 및 느린 네트워크 등록을 확인한다. 지원되지 않는 HEIC는 JPG 변환 안내가 표시되어야 한다.
2. Firebase Storage 서비스 활성화·과금 설정·현재 배포된 Storage 규칙·서비스 계정의 실제 bucket 접근 및 서명 권한을 운영 콘솔에서 확인한다. 코드 수정만으로 콘솔 설정을 보장하지 않는다.
3. 실제 부하 시험은 별도 테스트 프로젝트에서 단계적으로 한다. 성공률, p95 등록 지연, 429/503 비율, 심사 대기 시간, 저장소 비용을 관찰한다.
4. 파일 전송 후 등록을 끝내지 못한 비공개 고아 파일은 생길 수 있다. 정리는 ‘참조 여부 조사→유예 기간→검토’ 순으로 별도 작업한다. 이 수정에서는 사용자 파일을 일괄 삭제하지 않는다.
5. 악의적인 직접 Storage 생성 요청까지 저장량을 강제 제한하려면 서버 발급 업로드 예약과 규칙 연동이 추가로 필요하다. 현재는 공개 읽기나 본인 승인 우회를 열지 않으며, API 등록 5장 제한이 물리적 저장소 전체 사용량 제한은 아니다.
6. 인연 추천 풀 조회·전체 가입 폭증의 용량 보장은 사진 등록 보강과 별도다. 추천 쿼리·인덱스, 비용 알림, 심사 운영 인력을 함께 점검해야 한다.
